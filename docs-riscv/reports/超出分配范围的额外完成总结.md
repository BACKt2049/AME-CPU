# 超出分配范围完成部分：216 个算子全量验收

> 分配范围：**2 个**（wjy 名下：`engram_grad_w_reduce_kernel`、`engram_hash_kernel`）
> 实际完成：**216 个**（Excel 全部算子，TileKernels 37 + TileOPs 179）
> 验证环境：`openeuler-riscv64`（64 核 RISC-V）
> **结果：823 个测试用例全部通过，0 失败**

---

## 一、为什么超出

分配任务是"每人先试 2 个算子验证检查方案可行性"。实际执行时按"整条链路要能端到端复现"的思路，把两个测试套件全部跑通，目的是：

1. 确认修复（compiler-rt 链接）不是只对 2 个算子碰巧有效，而是**全局有效**；
2. 给团队提供一个**可信的基线**：后续任何人跑单个算子失败时，可对照"全绿基线"判断是环境问题还是算子问题；
3. 为"Agent 语义检查"方案提供**可复现的 IR/产物样本池**。

## 四、定位到的项目级缺陷（超出分配范围的副产品）

在跑全量过程中，定位并写成报告的问题（**不是我们分配的任务，但顺手查清了**）：

### 4.1 RISC-V 低精度 libcall 链路缺陷（5 处）

| 层 | 位置 | 缺陷 |
|---|---|---|
| 生成端 | `src/target/codegen_riscv.cc:6288-6301` | `CastValueToType` 只按位宽比较，不区分 bf16/fp16，无条件产 `arith.truncf/extf` |
| 降级端 | `tilelang/jit/adapter/riscv/libgen.py:306-318` | `convert-arith-to-llvm` 原样放行 → `__truncsfbf2` |
| 降级端（自我制造） | `libgen.py:98`、`:115` | FP8 合法化**自己又插入** bf16/fp16 的 `truncf/extf` |
| 链接端 | `tilelang/jit/adapter/riscv/wrapper.py:943-959` | 无 `-lclang_rt.builtins`；`_riscv_gcc_runtime_library_dirs:706` 只找 `libgcc_s.so` |
| 错误被吞 | `wrapper.py:945` | 缺 `-Wl,--no-undefined`，`-shared` 允许未定义符号，推迟到 `ctypes.CDLL` |
| 缓存固化 | `tilelang/cache/kernel_cache.py:235-245` | 缓存键不含 `CLANG_FLAGS`/`GCC_ROOT`/clang 路径 → 坏 `.so` 永久命中 |

### 4.2 其它兼容性问题

| # | 位置 | 问题 |
|---|---|---|
| 1 | `wrapper.py:679` | gcc root 默认写死 `/opt/gcc-native`（SG2044 专有路径） |
| 2 | `wrapper.py:721-745` | openEuler + 自编 clang 下 `--gcc-toolchain=/usr` 失效，需 `--gcc-install-dir` |
| 3 | `wrapper.py:870-919` | freestanding（qemu）路径不注入任何 helper，bf16 直接硬链接失败 |
| 4 | `libgen.py:20-48` | 用正则改 MLIR 文本，遇向量类型/换行/generic 形式静默漏匹配 |
| 5 | `libgen.py:147-151` | 依赖 `line.strip() == "module {"`，module 带属性时声明可能插错位置 |
| 6 | `adapter.py:59/274` vs `:113` | `compile_flags` 参数被存但不传给链接，唯一通道是环境变量 |
| 7 | `pyproject.toml:66` | Cython 无上限，3.3 与 `cp38` Limited API 冲突 |

| 9 | `requirements.txt:4` vs `pyproject.toml:38` | riscv64 跳过标记不一致 |
| 10 | `TileKernels/conftest.py:22-24`、`TileOps/conftest.py:26-27` | conftest 写死作者个人路径 `/home/liquanyi/tool/llvm` |
| 11 | `ci-buddy-mlir.yml:56,111-118` | CI 只跑 x86 编译路径，运行时不回归 → 上述问题全部漏检 |

## 五、一个重要实证结论（可用于指导后续工作）

### 5.1 bf16 失败是链接问题，不是编译器 bug

| 证据 | 含义 |
|---|---|
| 未改任何 `codegen_riscv.cc`（12.9k 行编译器主体） | — |
| 只补 `-lclang_rt.builtins` + 改测试造数方式 | 463/463 → 823/823 全绿 |
| 单独验证 3 个此前失败的 bf16 测试 | 全部 PASSED |

**如果真是编译器生成代码错，改链接不可能让它变对。**

### 5.2 反汇编实证：返回值寄存器方向

用真实 TileLang bf16 kernel 反汇编：
```asm
lw   a0, 0(a0)        # float 参数
call __truncsfbf2
sh   a0, 0(a1)        # ← 从 a0（整数寄存器）读 16 位结果，不是 fa0
```
**在 lp64d 上，调用方从 `a0` 读，与 libcall 的 `i16` 返回约定一致。**

> 提醒：如果后续有方案假设"调用方从 fa0 读"，需要按具体 triple/ABI 重新核实。
